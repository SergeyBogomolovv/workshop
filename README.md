# Мастерская

Учебное веб-приложение для записи на ремонт смартфонов, ноутбуков и планшетов. Клиент выбирает услугу и свободное время, следит за ремонтом и редактирует контакты. Администратор обрабатывает заявки и меняет их статусы.

Стек: **React + Vite + React Router + Tailwind CSS + TypeScript**, **Go + chi + sqlx + Squirrel + PostgreSQL**. Версии библиотек зафиксированы в `frontend/package-lock.json` и `backend/go.mod`, образы Docker — в Dockerfile и Compose.

## Запуск

Нужен Docker Desktop с Compose. Команды выполняются из корня проекта. Node и Go на компьютере для Docker-запуска не нужны.

```sh
docker compose up -d --build
```

Откройте **http://localhost:8088**. Порт привязан только к `127.0.0.1`; API и PostgreSQL доступны внутри Docker-сети. Дополнительная настройка браузера не нужна.

Первый запуск загружает образы, применяет миграцию и создаёт каталог из шести услуг. Последующие запуски сохраняют данные. Зависимости `service_healthy` не дают прокси стартовать раньше готовности API и базы.

### Локальные настройки

Файлы `.env` и `.secrets/` исключены из Git и Docker build context. В текущем рабочем каталоге `.env` уже заполнен. В новой копии проекта скопируйте `.env.example` в `.env` и заполните значения вручную: пароли БД, два независимых ключа из 32 байтов в Base64 и адрес приложения. Сохраняйте ключи из `.env` вместе с резервной копией БД: без `DATA_KEY` персональные поля не расшифровать, без `LOGIN_KEY` нельзя найти логины. Изменение паролей в `.env` не меняет роли в уже созданном PostgreSQL volume.

### Аккаунты

Зарегистрируйте клиента через интерфейс. Готовых паролей и аккаунтов по умолчанию нет.

Первого администратора создайте интерактивно:

```sh
docker compose exec api create-admin
```

Команда запросит логин, имя, телефон, email, согласие с политикой и пароль. Ввод пароля скрыт; минимум — 15 символов. После входа администратору доступна страница `/admin/appointments`. Это роль приложения, отдельная от одноимённой сервисной роли БД.

### Управление стендом

```sh
docker compose ps
docker compose logs --tail=50 api
docker compose stop
docker compose start
```

Для пересборки изменений повторите `docker compose up -d --build`. Обычный `docker compose down` удаляет контейнеры, сохраняя volume БД. Не добавляйте `--volumes`, если данные нужно сохранить.

## Что работает

- Публичный каталог с фильтрами по устройству, регистрация, вход и выход.
- Профиль клиента: имя, телефон, email.
- Запись на ближайшие 30 дней, слоты 10:00–17:00 по Москве. Один слот — одно устройство.
- Собственные заявки, история статусов и отмена до начала ремонта.
- Кабинет администратора: фильтр по статусу, пагинация, контакты и обработка заявки.
- Политики данных и cookie, уведомление первого посещения, адаптивная вёрстка, страница 404.

Статусы: **Новая → Принята → В работе → Готова → Выдана**. Отмена доступна только из «Новая» и «Принята». При одновременной записи на один слот БД разрешает только одну заявку; отмена освобождает время.

## Архитектура

```text
frontend/src/
  app/                 маршруты, оболочка и состояние сессии
  api/                 HTTP-клиент, типы и загрузка ресурсов
  components/          общие элементы интерфейса
  features/            переиспользуемые части форм
  pages/               страницы гостя, клиента и администратора
  styles/              CSS и Tailwind
  test/                DOM-тесты и HTML-валидация
backend/
  cmd/api/             сборка зависимостей и запуск HTTP
  cmd/create-admin/    интерактивное создание администратора
  internal/domain/     модели и публичные ошибки
  internal/handler/    разбор HTTP и ответы
  internal/middleware/ сессии, CSRF, Origin, лимиты
  internal/service/    бизнес-правила и интерфейс Repository
  internal/repository/postgres/ sqlx, Squirrel, транзакции
  internal/security/   AES-GCM, Argon2id, токены и HMAC
  internal/config/     проверка переменных окружения
  internal/integration/ тесты HTTP, PostgreSQL и запущенного приложения
  migrations/          атомарная миграция схемы и каталога
infra/
  postgres/            начальная настройка ролей и прав
  proxy/               HTTP, CSP и раздача frontend
```

Сервис не зависит от chi, sqlx или Squirrel. Реализация репозитория подключается в `cmd`. Контакты шифруются до передачи в repository и расшифровываются после проверки доступа. Повторные чтения пользователя и сессии используют подготовленные statements; остальные запросы параметризованы. История и заявка записываются в одной транзакции.

`package.json` описывает зависимости и команды; `package-lock.json` фиксирует их дерево; `tsconfig.json` включает строгую типизацию. Эти JSON-файлы и сгенерированный `go.sum` не содержат комментариев из-за формата. Остальные авторские модули и именованные функции документированы в исходниках.

## Защита данных

- Пароли: Argon2id, 19 МиБ, два прохода, индивидуальная соль.
- Логин, имя, телефон, email и описание: AES-256-GCM, случайный nonce, привязка к записи и полю. Поиск логина — HMAC отдельным ключом.
- Авторизация: случайный 256-битный токен в `workshop_session`, `HttpOnly`, `SameSite=Lax`; в БД — SHA-256 токена. Сессия живёт 24 часа и отзывается при выходе.
- На каждом API-запросе проверяется переданная сессия, на защищённых маршрутах — доступ. Роль читается из БД. Чужая заявка возвращает 404.
- Изменения требуют точный `Origin`, а после входа — ещё и `X-CSRF-Token`. Запросы ограничены 16 КиБ; сервер проверяет поля и отклоняет неизвестные JSON-ключи.
- Лимиты входа действуют отдельно по IP и логину, регистрации — по IP; окно 15 минут. Значения задаются в `.env`. In-memory limiter рассчитан на один экземпляр API.
- CSP не разрешает inline JS/CSS и `eval`. Есть `nosniff`, Referrer-Policy и Permissions-Policy.
- PostgreSQL: `user` обслуживает приложение, `admin` выполняет миграции, `bootstrap` нужен для начальной настройки. `user` не может создавать таблицы/роли или изменять каталог и историю. `admin` не суперпользователь.

Публичный `GET /api/v1/auth/session` возвращает `{ "user": null }` для гостя, чтобы начальная загрузка не порождала ожидаемый 401. `/auth/me` остаётся защищённым.

## Проверки

### Стиль кода

Общие отступы заданы в `.editorconfig`: Go — табуляция с шириной 4, SQL/nginx — 4 пробела, TypeScript/TSX/CSS/JSON/YAML — 2 пробела. Комментарии пишутся на русском. Длинные литералы и вызовы оформляются на нескольких строках, логические блоки разделяются пустой строкой. Условия JavaScript и TypeScript всегда используют фигурные скобки; сложные ветвления не следует прятать во вложенных тернарных выражениях JSX.

Prettier использует настройки `.prettierrc.json`; Go форматируется через goimports и golines с целевой длиной строки 100 символов. SQL, Dockerfile и nginx оформляются вручную с сохранением структуры блоков. Версии Go-форматтеров закреплены в Makefile.

```sh
make format
make format-check
```

Перед этими командами выполните `npm ci` в `frontend`. При первом запуске Go загрузит форматтеры в свой кэш. `make format-check` проверяет стиль без изменения файлов. В редакторе используйте форматтер, совместимый с `.editorconfig`, и форматирование при сохранении.

### Автоматические проверки

На компьютере с Node 22.12+:

```sh
cd frontend
npm ci
npm run check
npm run test
npm run build
npm run validate:css
npm run format:check
```

`npm run test` проверяет формы и маршруты в jsdom, валидирует HTML всех семейств страниц и требует отсутствие `console.log`, `console.warn`, `console.error` в этих сценариях. Это компонентная проверка, а не замена полного обхода браузера. `validate:css` проверяет синтаксис сборки и грамматику авторских CSS-деклараций; Tailwind-директивы проверяет сборщик.

На компьютере с Go 1.26+:

```sh
cd backend
go test -race ./...
go vet ./...
```

Из корня проекта, при запущенном стенде:

```sh
docker compose -f compose.yml -f compose.test.yml run --rm tests
docker compose -f compose.yml -f compose.test.yml run --rm -e TEST_BASE_URL=http://web tests
```

Обе команды запускают существующий интеграционный сценарий на Go с настоящим PostgreSQL: конкурентные регистрации/бронирования, IDOR, CSRF, срок и отзыв сессий, историю, откат транзакций и права ролей. Первая поднимает тестовый HTTP-сервер в процессе теста. Вторая с `TEST_BASE_URL=http://web` обращается к уже запущенному приложению через nginx и дополнительно проверяет заголовки прокси. Проверка cookie использует отдельное хранилище `net/http/cookiejar`. Тесты создают случайные учебные аккаунты и удаляют только свои записи.

`npm run dev` запускает Vite для разработки интерфейса с перенаправлением API на локальный стенд. Все сценарии с авторизацией доступны на основном адресе http://localhost:8088.

Стенд рассчитан на локальное использование. Публикация в интернете в задачу не входит.
